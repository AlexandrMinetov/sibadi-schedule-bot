# СибАДИ — БИ-22Э1

Существующий Telegram-бот @SibADI_BI22E1_bot для группы 14992. Источник — официальный API СибАДИ. Работает только в настроенной теме «Расписание». Обычные сообщения, другие темы и команды другим ботам игнорируются. Анализа переписки нет.

## Cloudflare Workers

- `/today`, `/tomorrow`, `/week` (понедельник–воскресенье), `/help` — через Telegram webhook.
- Ежедневная публикация на завтра — первый успешный Cron после 20:00 по Омску (14:00 UTC). После пропущенного вечера бот догоняет публикацию на сегодня.
- Проверка изменений сегодня/завтра — `*/15 * * * *` UTC. На границе недель каждая неделя проверяется независимо.
- Автоматическая публикация закрепляется, открепляется только прежнее известное закрепление этого бота. Отсутствие прав не мешает отправке. Ответы на команды не закрепляются.
- Пустой/неверный ответ API не трактуется как отмена занятий. Неделя без единого занятия требует проверки источника и не объявляется автоматически пустой.

`wrangler.jsonc` обновляет **существующий** Worker `sibadi-schedule-bot`; домен покупать не нужно. Состояние — один SQLite Durable Object `ScheduleBot`, binding `BOT`. Доступен на Workers Free; при превышении бесплатных квот Cloudflare операции прекращаются. См. [бесплатный тариф и лимиты](https://developers.cloudflare.com/durable-objects/platform/pricing/).

KV `SIBADI_STATE` сохранён как `LEGACY_STATE` для однократного переноса. Его ID в конфигурации не является секретом. Не удаляйте старое хранилище до завершения перехода. Секреты `BOT_TOKEN`, `CHAT_ID`, `THREAD_ID`, `WEBHOOK_SECRET` остаются в Cloudflare Secrets, при деплое не заменяются. `WEBHOOK_SECRET`: 32–256 символов `A-Z a-z 0-9 _ -`. Не помещайте секреты в git, URL, логи или сообщения. Опциональный `BOT_USERNAME` — без `@`.

## Переход без двух работающих сервисов

1. Развернуть новую версию. Durable Object по умолчанию неактивен; старый KV-флаг не включает его автоматически. На `/` должна возвращаться `version: 2`.
2. Выполнить `/check`: проверка API СибАДИ, личности существующего бота, webhook и записи состояния, без отправки сообщений.
3. Только после успешного `/check` отключить старый workflow `Schedule bot` в GitHub Actions или убрать его `schedule`. Дождаться завершения уже запущенных/стоящих в очереди запусков. Не запускать Python polling после включения webhook.
4. Получить актуальный `state.json` из main после последнего старого запуска. Выполнить `/import`: переносятся только расписание, признаки публикации, ID сообщений бота и его закрепления. KV имеет приоритет над Python-снимком. Смещения updates, тексты и отправители не переносятся. Повторный импорт ничего не перезаписывает.
5. Выполнить `/check`, затем `/activate` (проверка действует 15 минут). Активация регистрирует команды и webhook, проверяет адрес через `getWebhookInfo`, затем включает мониторинг. Старые updates не сбрасываются.
6. Проверить четыре команды в настоящей теме. После планового запуска проверить `/status`: `lastCronAt`, `lastCronSuccessAt`, `lastCommandAt`, `pending`. Фактическую вечернюю отправку подтверждать отдельно по сообщению в теме.

Адрес существующего Worker: `https://sibadi-schedule-bot.vkspaz780.workers.dev`.

```powershell
# Скрипт вводит секрет скрыто, не сохраняет его в файл.
./scripts/manage.ps1 -Action check
./scripts/manage.ps1 -Action import
./scripts/manage.ps1 -Action activate
./scripts/manage.ps1 -Action status
```

Маршруты `POST /check`, `/status`, `/import`, `/activate`, `/deactivate`, `/resolve` требуют `Authorization: Bearer <WEBHOOK_SECRET>`. Telegram использует `POST /telegram` с `X-Telegram-Bot-Api-Secret-Token`. `/deactivate` сначала выключает мониторинг, затем удаляет webhook. Публичных маршрутов ручной рассылки или Cron нет.

## Защита от повторов и восстановление

Durable Object последовательно выполняет запросы, включая сетевые ожидания; записи отправок переживают перезапуск объекта. Перед отправкой сохраняется техническое намерение, после успеха — ID сообщения. Повторные части `/week` не отправляются повторно. Состояние не содержит текстов пользователей или ID отправителей. Обычные технические записи имеют срок хранения, истёкшие записи очищаются ежедневно.

Telegram не предоставляет идемпотентный `sendMessage`: строго гарантировать одновременно отсутствие потерь и повторов при обрыве между Telegram и хранилищем нельзя. При неизвестном результате отправка остаётся `pending`, **не повторяется автоматически** и видна в `/status`. Оператор проверяет тему и вызывает `/resolve`:

```json
{"operation":"daily:2026-11-18","action":"delivered","messageId":123}
```

Либо `{"operation":"daily:2026-11-18","action":"retry"}`, только убедившись, что сообщения нет. Публикация/уведомление продолжится на следующем Cron. Для ответа на команду после разрешения неизвестной отправки проще отправить новую команду. Подтверждённый отказ Telegram (4xx) допускает повторную попытку с учётом `retry_after`. Неудачное редактирование ежедневного сообщения повторяется на следующей проверке без нового уведомления.

## Резервная Python-версия

`bot.py`, `state.json`, `.github/workflows/schedule.yml` сохранены. До подтверждения перехода расписание старого workflow не отключается изменением исходников. После перехода запускать резервную версию только после `/deactivate` и переноса актуального состояния обратно. Режимы: `preview`, `diagnose`, `poll`, `test`, `publish_today`. GitHub Actions может задерживаться и не является подтверждённой заменой Cron Cloudflare.
